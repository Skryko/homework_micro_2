## Задача 1. Обеспечить разработку

### Предлагаемое решение

Для организации процесса разработки предлагается использовать:

- **GitLab Cloud** — облачная система хранения исходного кода;
- **GitLab CI/CD** — система непрерывной интеграции и непрерывной поставки;
- **GitLab Runner** — агенты для выполнения сборок;
- **GitLab Container Registry** — хранилище Docker-образов;
- **CI/CD Variables** — безопасное хранение секретов.

GitLab Cloud позволяет организовать полный цикл разработки микросервисов: хранение кода, запуск сборок, выполнение тестов, создание Docker-образов и последующую поставку приложения в нужное окружение.

### Принцип организации репозиториев

В микросервисной архитектуре каждый сервис должен храниться в отдельном Git-репозитории.

Пример структуры:

- `service-auth` — отдельный репозиторий
- `service-payment` — отдельный репозиторий
- `service-notification` — отдельный репозиторий
- `service-order` — отдельный репозиторий

Такой подход позволяет независимо разрабатывать, тестировать, собирать и разворачивать каждый микросервис.

### Взаимодействие компонентов

1. Разработчик делает **push**, **merge request** или создаёт **tag** в GitLab Repository.
2. GitLab получает событие из системы контроля версий и запускает **GitLab CI/CD Pipeline**.
3. **GitLab Runner** выполняет jobs, описанные в pipeline: тесты, сборку, создание Docker-образа и деплой.
4. После успешной сборки Docker-образ публикуется в **GitLab Container Registry**.
5. Далее образ может быть развёрнут в нужное окружение: **dev**, **stage** или **prod**.

### Пример pipeline

Pipeline может состоять из следующих этапов:

- `test` — запуск тестов;
- `build` — сборка приложения;
- `docker build` — создание Docker-образа;
- `docker push` — публикация Docker-образа в registry;
- `deploy` — развёртывание приложения в нужное окружение.

### Соответствие требованиям

| Требование | Реализация |
|---|---|
| Облачная система | Используется GitLab Cloud |
| Система контроля версий Git | GitLab использует Git |
| Репозиторий на каждый сервис | Для каждого микросервиса создаётся отдельный репозиторий |
| Запуск сборки по событию из системы контроля версий | Pipeline запускается при push, merge request или создании tag |
| Запуск сборки по кнопке с указанием параметров | В GitLab можно запускать pipeline вручную и передавать переменные |
| Возможность привязать настройки к каждой сборке | Настройки задаются в pipeline, variables и environments |
| Возможность создания шаблонов для различных конфигураций сборок | Используются общие CI/CD templates |
| Возможность безопасного хранения секретных данных | Используются masked/protected CI/CD Variables |
| Несколько конфигураций для сборки из одного репозитория | Можно описать разные jobs для dev, stage и prod |
| Кастомные шаги при сборке | Любые команды можно описать в pipeline |
| Собственные Docker-образы для сборки проектов | Для каждой job можно указать собственный Docker image |
| Возможность развернуть агентов сборки на собственных серверах | Используются self-hosted GitLab Runner |
| Возможность параллельного запуска нескольких сборок | GitLab Runner поддерживает параллельное выполнение jobs |
| Возможность параллельного запуска тестов | Тесты можно разделять на несколько параллельных jobs |

### Обоснование выбора

GitLab Cloud выбран потому, что он закрывает почти все требования одной платформой.
В нём есть Git-репозитории, CI/CD, хранение секретов, шаблоны pipeline, ручной и автоматический запуск сборок, работа с Docker-образами и возможность подключения собственных runners.

Это удобно для микросервисной архитектуры, потому что каждый сервис может иметь собственный репозиторий, собственный pipeline и независимый жизненный цикл разработки.
При этом общие шаблоны сборок позволяют стандартизировать процесс для всей команды.

## Задача 2. Логи
### Предлагаемое решение

Для сбора и анализа логов предлагается использовать стек:

- **Grafana Loki** — центральное хранилище логов;
- **Promtail** или **Grafana Alloy** — агенты для сбора логов;
- **Grafana** — пользовательский интерфейс для поиска и анализа логов.

Приложения должны писать логи в `stdout` и `stderr`.
Это минимизирует требования к самим приложениям.
Сбором логов занимается инфраструктурный агент, установленный на каждом хосте или запущенный в Kubernetes как `DaemonSet`.

### Взаимодействие компонентов

1. Микросервис пишет логи в `stdout` и `stderr`.
2. Docker или Kubernetes сохраняет `container logs`.
3. Promtail или Grafana Alloy читает эти логи на каждом хосте.
4. Затем агент отправляет логи в Grafana Loki.
5. Grafana Loki хранит логи в центральном хранилище.
6. Разработчики и DevOps-инженеры используют Grafana для поиска, фильтрации и анализа логов.

### Принцип работы

Каждый микросервис пишет логи в стандартный поток вывода: `stdout` и `stderr`.

Promtail или Grafana Alloy собирает эти логи с хостов и отправляет их в Grafana Loki.
Loki хранит логи централизованно и позволяет выполнять поиск с помощью языка запросов **LogQL**.

Grafana подключается к Loki как источник данных и предоставляет разработчикам веб-интерфейс для анализа логов.

### Пример labels для логов

Для удобного поиска логам назначаются labels:

text
service="auth"
environment="prod"
host="worker-01"
container="service-auth"
namespace="production"
Пример запроса LogQL

{service="auth", environment="prod"} |= "ERROR"

Такой запрос покажет ошибки только по сервису auth в production-окружении.

Соответствие требованиям
| Требование                                        | Реализация                                                               |
| ------------------------------------------------- | ------------------------------------------------------------------------ |
| Сбор логов в центральное хранилище со всех хостов | Все логи отправляются в Grafana Loki                                     |
| Минимальные требования к приложениям              | Приложения только пишут логи в stdout/stderr                             |
| Сбор логов из stdout                              | Promtail / Alloy читает container logs                                   |
| Гарантированная доставка логов                    | Агент хранит позицию чтения логов и продолжает отправку после сбоя       |
| Поиск и фильтрация по записям логов               | Используется LogQL в Grafana Loki                                        |
| Пользовательский интерфейс для разработчиков      | Используется Grafana                                                     |
| Возможность предоставить доступ разработчикам     | В Grafana настраиваются пользователи, команды и права доступа            |
| Возможность дать ссылку на сохранённый поиск      | В Grafana можно сохранить Explore-запрос или dashboard и передать ссылку |

Обоснование выбора

Grafana Loki выбран потому, что он хорошо подходит для микросервисной архитектуры и контейнерной среды.
Приложениям не требуется реализовывать сложную интеграцию с системой логирования.
Они просто пишут логи в stdout и stderr, а инфраструктура сама собирает и доставляет их в центральное хранилище.

Loki экономичнее классического ELK-стека, потому что не индексирует полный текст каждой строки лога, а использует labels.
Это снижает требования к ресурсам при большом количестве микросервисов.

Grafana используется как единый интерфейс для логов и мониторинга.
Разработчики могут самостоятельно искать ошибки по сервису, окружению, хосту, контейнеру или namespace.

## Задача 3. Мониторинг

### Предлагаемое решение

Для мониторинга предлагается использовать стек:

• Prometheus — сбор и хранение метрик;
• Node Exporter — сбор метрик хостов;
• cAdvisor — сбор метрик контейнеров;
• Servic


e Exporters — сбор специфичных метрик сервисов;
• Grafana — визуализация и dashboard;
• Alertmanager — отправка уведомлений об авариях.


Взаимодействие компонентов

1. Node Exporter устанавливается на каждый хост и собирает метрики хоста.
2. cAdvisor собирает метрики контейнеров и потребление ресурсов каждым сервисом.
3. Сами приложения или отдельные exporters отдают специфичные метрики сервисов через endpoint /metrics.
4. Prometheus периодически опрашивает Node Exporter, cAdvisor и endpoints приложений.
5. Grafana подключается к Prometheus как источник данных и отображает dashboard.
6. Alertmanager получает алерты от Prometheus и отправляет уведомления ответственным инженерам.

Принцип работы

Prometheus работает по pull-модели.
Он периодически опрашивает endpoint'ы с метриками и сохраняет полученные данные в свою базу.

Для хостов устанавливается Node Exporter.
Он собирает системные метрики: CPU, RAM, диски и сеть.

Для контейнеров используется cAdvisor.
Он собирает потребление ресурсов каждым контейнером.

Для специфичных метрик сервисов приложение может отдавать endpoint /metrics.
Например, сервис может отдавать:

• количество HTTP-запросов;
• время ответа;
• количество ошибок;
• количество сообщений в очереди;
• длительность запросов к базе данных.

Метрики хостов

Node Exporter собирает следующие метрики:

• CPU usage
• Load average
• RAM usage
• Swap usage
• Disk usage
• Disk I/O
• Network traffic
• Network errors
• Filesystem usage

Метрики контейнеров и сервисов

cAdvisor собирает следующие метрики:

• CPU usage per container
• Memory usage per container
• Network traffic per container
• Filesystem usage per container
• Container restart information
• Container lifecycle metrics

Специфичные метрики сервисов

Примеры прикладных метрик:

• http_requests_total
• http_request_duration_seconds
• orders_created_total
• payments_failed_total
• queue_messages_total
• database_query_duration_seconds

Примеры PromQL-запросов

CPU по контейнерам:
rate(container_cpu_usage_seconds_total[5m])

Использование памяти контейнерами:
container_memory_usage_bytes

Свободное место на диске:
node_filesystem_avail_bytes

Количество HTTP-запросов по сервису:
sum(rate(http_requests_total[5m])) by (service)

Ошибки HTTP 5xx:
sum(rate(http_requests_total{status=~"5.."}[5m])) by (service)

Соответствие требованиям
| Требование                                | Реализация                                     |
| ----------------------------------------- | ---------------------------------------------- |
| Сбор метрик со всех хостов                | Node Exporter устанавливается на каждый хост   |
| Сбор CPU, RAM, HDD, Network хостов        | Node Exporter собирает системные метрики       |
| Сбор ресурсов для каждого сервиса         | cAdvisor собирает container-level метрики      |
| CPU, RAM, HDD, Network каждого сервиса    | cAdvisor отдаёт метрики по каждому контейнеру  |
| Сбор специфичных метрик каждого сервиса   | Сервисы публикуют endpoint /metrics            |
| UI с возможностью делать запросы          | Grafana и Prometheus поддерживают PromQL       |
| UI с возможностью агрегировать информацию | PromQL позволяет агрегировать данные по labels |
| UI с возможностью настраивать панели      | Grafana позволяет создавать dashboard          |

Обоснование выбора

Prometheus выбран как основная система мониторинга, потому что он хорошо подходит для микросервисной и контейнерной архитектуры.
Он умеет собирать метрики с большого количества сервисов, хостов и exporters.

Node Exporter закрывает мониторинг физических и виртуальных серверов.
cAdvisor закрывает мониторинг контейнеров.
Service Exporters позволяют собирать специфичные метрики приложений, баз данных, брокеров сообщений и других компонентов.

Grafana выбрана как основной пользовательский интерфейс, потому что позволяет создавать разные dashboard для эксплуатации, разработки и дежурных инженеров.
В Grafana можно строить панели по состоянию хостов, сервисов, баз данных, очередей, ошибок и времени ответа.

Alertmanager используется для отправки уведомлений при авариях.


Например, при высокой загрузке CPU, нехватке RAM, заполнении диска, недоступности сервиса, росте HTTP 5xx или увеличении времени ответа.

Итоговое решение

Для организации инфраструктуры разработки и эксплуатации микросервисной системы предлагается следующий стек:

| Направление              | Решение                   |
| ------------------------ | ------------------------- |
| Хранение исходного кода  | GitLab Cloud              |
| CI/CD                    | GitLab CI/CD              |
| Выполнение сборок        | GitLab Runner             |
| Хранение Docker-образов  | GitLab Container Registry |
| Логи                     | Grafana Loki              |
| Сбор логов               | Promtail / Grafana Alloy  |
| Интерфейс логов          | Grafana                   |
| Метрики                  | Prometheus                |
| Метрики хостов           | Node Exporter             |
| Метрики контейнеров      | cAdvisor                  |
| Визуализация мониторинга | Grafana                   |
| Уведомления              | Alertmanager              |

Выбранный стек закрывает требования по разработке, логированию и мониторингу.
Он подходит для микросервисной архитектуры, потому что позволяет независимо разрабатывать и разворачивать сервисы, централизованно собирать логи и метрики, а также предоставлять разработчикам и DevOps-инженерам удобный интерфейс для анализа состояния системы.
